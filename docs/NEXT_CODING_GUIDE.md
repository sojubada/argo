## A. 대체 글꼴 글자 폭 보정

목표: 원본 글꼴이 없을 때도 줄 나눔이 원본과 같은 자리에서 일어나게 한다.

1. 측정 도구: `tools/measure_advances.py`(신규, 컨테이너에서만 실행)
   - 입력: PC 기준 PDF, Argo PDF. pdfplumber로 글자 클래스(한글·영문·숫자·공백)별 `(x1-x0)/size` 중앙값을 출력한다.
   - 글꼴 크기 8pt 미만 글자는 제외한다.
2. 글자 폭 프로필(신규 `rust/argoconv/src/fontprofile.rs`)
   - 키: 원본 글꼴 이름(정규화). 값: `{hangul, latin, digit, space}` 목표 폭(em).
   - 초기 값: 맑은 고딕·MalgunGothic 계열 한글 1.00 / Arial 영문 0.556 / 숫자 0.556 / 공백 0.278. 함초롬 계열 한글 0.97.
   - 값은 위 측정 스크립트 결과로만 채운다. 추측으로 넣지 않는다. 모르는 글꼴은 한글 1.00, 나머지는 보정하지 않는다.
3. 적용 방식
   - 배치(줄 나눔) 단계: 글자 진행 폭을 `max(실제, 목표)`가 아니라 목표 값으로 맞춘다. 실제와의 차이는 자간으로 분배한다.
   - 그리기 단계: 글자 모양은 가로 배율 `min(목표/실제, 1.08)`까지만 늘린다. 그 이상은 자간으로만 보정한다(글자가 뭉개지지 않게).
   - 원본 글꼴이 실제로 있으면(사용자 폴더 글꼴) 보정하지 않는다.
4. 적용 위치
   - 발표: `rust/argoconv/src/slides/fontbook.rs`의 `advance()`에 프로필 조회를 넣는다. `text.rs`의 `break_lines`는 이미 이 함수를 쓰므로 수정을 최소화한다. 기존 15% 초과 허용(`overflow_ok_until`)과 겹치지 않는지 확인한다.
   - 워드: `rust/vendor/minipdf/src/docx.rs`의 글자 폭 측정 지점을 찾아 같은 함수를 부른다. 표 칸 줄 수가 달라지므로 표 계산도 같은 함수를 써야 한다.
   - 한글 hwp·hwpx: `rust/vendor/rhwp` 안의 글자 폭 계산을 먼저 읽고, 훅을 넣을 수 있는지 판단한다. 로컬에서 빌드하지 않는다(CI에서만). 불가능하면 이 항목은 보류하고 이유를 기록한다.
5. 완료 기준(목표값, 달성 여부는 측정으로 판단)
   - 춘천 29쪽, 월성 4쪽, NDA 9쪽 유지.
   - 쪽별 차이 중앙값: 춘천 3.6% → 2.5% 이하, VISION 2.2% → 1.8% 이하.
   - 기존 시험(minipdf 121개, slides 5개) 통과. 워드 견본 39개 변환 실패 0.
6. 함정
   - 이미 맞춰 둔 줄 높이(맑은 고딕 1.73배)와 단락 간격 규칙을 건드리지 않는다.
   - 폭을 키우면 NDA처럼 이미 맞은 문서가 어긋날 수 있다. 변경 전후로 NDA·VISION 대표 쪽을 반드시 비교한다.

## B. 스펙트럼 레벨 적응

근거: 6회 재생 모두 탭이 정상 동작했다. 그런데도 막대가 안 나온다면 신호 크기가 고정 창을 벗어났을 가능성이 크다. 현재 `analyse()`는 고정 창 `(dB+62)/52`를 쓴다. 조용한 음원은 전 대역이 0으로 잘려 최소 높이(3pt)만 그려진다.
확인되지 않은 것: 어느 곡에서 어떤 값이 나왔는지는 로그에 없다. D에서 값을 남겨 확정한다.

1. `Spartan/FileOpeners/MusicVisuals.swift` `analyse()`
   - 대역 최댓값의 느린 추적값(`runningPeak`)을 둔다. 올라갈 때는 빠르게, 내려갈 때는 약 5초 시정수로 천천히.
   - 매핑: `(db - (runningPeakDb - 52)) / 52`. 상한 보정은 `runningPeakDb`가 -70 dB 미만이면 무음으로 보고 올리지 않는다(무음에서 잡음이 커지는 것 방지).
2. 채널: 비인터리브 버퍼는 채널이 별도 버퍼로 온다. 현재는 첫 버퍼만 쓴다. 모든 버퍼를 평균해서 쓴다(한쪽 채널이 비는 음원 대비).
3. 완료 기준: 조용한 곡과 큰 곡 모두에서 막대 최대 높이가 칸의 70% 이상에 도달하고, 무음 구간에서는 최소 높이로 내려간다.
4. 함정: 오디오 스레드에서 호출되므로 새 할당·로그를 넣지 않는다. 기존 `lock` 규칙을 지킨다.

## C. A 적용 뒤 재측정 항목

- 춘천 14쪽: PC는 표 머리줄("구분/'25 실적/'26 목표…")이 같은 쪽에 있고 Argo는 앞 쪽으로 밀려 있다. 쪽 흐름 차이이므로 A 이후 먼저 확인한다.
- 표 칸 안 줄바꿈: "32명(의무교육 대상)", "4,118백만원(13명)" 칸의 줄 수가 PC와 다르다. A로 해결되는지 본다.
- 안 풀리면: 표 칸 안쪽 여백과 칸 폭 계산을 PC 값과 대조한다.
- 월성 hwp 3쪽: 표가 있는 쪽의 위치는 비슷하다. 4쪽째가 어디서 시작하는지 PC 쪽 내용과 대조한다.

## E. 문서 쓰기 기능 (구현 여부 미확인)

요청 범위: hwpx·docx·pptx 텍스트 수정, xlsx 간단 숫자 재입력. 이번 기록에서는 구현 여부를 확인하지 못했다.
1. 먼저 코드에서 현재 쓰기 지원 범위를 조사해 표로 정리한다(조사만, 코드 변경 없이).
2. 그 표를 Rob에게 보고하고 범위·우선순위를 정한 뒤 구현한다.
3. 쓰기 방식 원칙: 원본 파일을 직접 덮어쓰지 않고 복사본에 쓴다. 원본의 XML은 수정할 텍스트 노드만 바꾸고 나머지는 그대로 보존한다.

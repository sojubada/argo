커밋 `c3f6811` 기준. 제미나이가 지적한 **9건**을 하나씩 확인했습니다.

**결론: 4건 반영, 4건 논박, 1건은 질문이 답을 못 받았습니다.**

## 반영할 것

### ① [상] 받은 함 폴링이 메인 스레드에서 돕니다 — 확인된 결함

제미나이 지적이 **정확합니다.** 코드로 확인했습니다.

```objc
sTimer = [NSTimer scheduledTimerWithTimeInterval:kPollInterval
                                         repeats:YES
                                           block:^(NSTimer *t) { [self tick]; }];
```

`scheduledTimer` 는 **메인 런루프**에 붙습니다. 그리고 `tick` 이 부르는
`inboxFingerprint` 는 `enumeratorAtPath` 로 **동기 디스크 I/O** 를 합니다.
2초마다 메인 스레드가 디스크를 훑습니다. 받은 함이 커질수록 나빠집니다.

제가 4,000개에서 끊도록 해 둔 것은 **양을 줄였을 뿐 위치가 틀린 것을 고치지
못합니다.** 뒷줄로 옮기고 결과만 메인으로 올려야 합니다.

### ② [상] 수신 컨트롤러를 1픽셀로 가린 것

제미나이 주장: `SFAirDropReceiverViewController` 는 전송 진행률과
**수락/거절 버튼을 띄우는 UI 컴포넌트**라서, 1픽셀로 가리면 사용자가 수락할
방법이 없어 전송이 영원히 대기한다.

**이 주장 자체를 확인할 길은 없습니다.** 비공개 API 의 내부 동작이고,
제미나이도 애플 문서를 인용한 것이 아니라 단정한 것입니다.

**그럼에도 반영합니다.** 근거는 제미나이의 주장이 아니라 이것입니다 —
**검증 앱은 전체 화면으로 `present` 했고, 그 상태에서 수신이 확인됐습니다.**
검증된 경로에서 벗어난 것은 제가 만든 1픽셀 방식이고, 저는 그것이 통할
근거를 갖고 있지 않습니다. 제가 제출 자료에 "근거가 없습니다"라고 적은
그대로입니다. **근거 없는 쪽이 물러나는 것이 맞습니다.**

### ③ [상] 받는 중에는 연장이 안 됩니다

제미나이 주장: `sharingd` 는 받는 동안 임시 폴더에 쓰고 **완료된 뒤에야**
받은 함으로 원자적 이동을 한다. 그래서 전송 중에는 크기·개수가 변하지 않아
1분 뒤 강제 종료된다.

구체적 경로(`/var/mobile/Library/Caches/com.apple.sharingd`)는 확인할 수
없습니다. 다만 **"받는 중에는 미완성 파일이 목적지에 보이지 않는다"는 원칙은
파일 수신의 일반적 구현**이고, 그렇다면 제 연장 장치는 **작동하지 않습니다.**

②와 ③은 **같은 해결로 수렴합니다** — 받기를 "보이는 화면"으로 만들면
화면이 떠 있는 동안 열어 두면 되고, 폴링으로 추측할 필요가 없어집니다.

### ⑥ [하] `/var/tmp` 표 항목

**제 표가 틀렸습니다.** 제가 파이썬으로 규칙을 흉내 낼 때
`NSTemporaryDirectory()` 자리에 `/private/var/tmp` 를 넣었는데, 그건
**제 가정이지 그 함수의 실제 반환값이 아닙니다.**

다만 제미나이 설명에도 불확실한 부분이 있습니다. Argo 는
`com.apple.private.security.no-container` 권한을 갖고 있어서 컨테이너가
없는 상태입니다. 그 경우 `NSTemporaryDirectory()` 가 무엇을 돌려주는지는
**저도 제미나이도 확인하지 않았습니다.**

**실질적으로는 영향이 없습니다.** 반환값이 컨테이너 tmp
(`/var/mobile/Containers/Data/Application/<UUID>/tmp/`)라면
`/var/mobile` 규칙으로 이미 safe 이고, `/var/tmp` 라면 caution 입니다.
어느 쪽이든 **그 `safePrefixes` 항목은 있으나 마나**입니다.
→ 표에서 그 줄을 지우고, 코드의 항목도 지우는 쪽이 정직합니다.

### ⑤ [하] 텍스트 뷰어의 `contentSize`

`attributedText` 대입 직후에는 레이아웃이 끝나지 않아 `contentSize` 가 0 일
수 있다는 지적은 맞습니다. `layoutIfNeeded()` 를 끼우는 것은 싸고 안전합니다.
반영합니다.

## 논박할 것

### ① [최우선] PDF 흰 화면 = 좌표계 이중 뒤집기 — **아닙니다**

제미나이 주장: `translateBy` + `scaleBy(1,-1)` 로 이미 뒤집은 컨텍스트에
`getDrawingTransform` 을 `concatenate` 하면 좌표가 왜곡되어 잉크가 캔버스
밖으로 날아간다.

**두 가지로 반박합니다.**

#### 반박 1 — 증상이 그 코드보다 먼저 있었습니다 (저장소로 확인)

흰 화면이 보고된 것은 **build 130** 입니다. 그 빌드의 렌더링 코드를
저장소에서 그대로 꺼내 보면:

```
$ git show 0223c0a:Spartan/FileOpeners/Readers/ArgoPDFReader.swift \
    | grep -n "CGContext(data:\|UIGraphicsImageRenderer\|translateBy\|scaleBy"

218:        guard let ctx = CGContext(data: nil,
```

**`translateBy` 도 `scaleBy` 도 없습니다.** 직접 만든 `CGBitmapContext` 는
원점이 왼쪽 아래라 PDF 와 같아서 뒤집기를 하지 않았습니다.

제미나이가 분석한 뒤집기 코드는 **흰 화면을 보고 받은 뒤에 제가 집어넣은
것**입니다. 증상보다 나중에 생긴 코드가 그 증상의 원인일 수 없습니다.

#### 반박 2 — 뒤집기 + `getDrawingTransform` 은 표준 조합입니다

둘은 **다른 일**을 합니다.

| | 하는 일 |
| --- | --- |
| `translateBy` + `scaleBy(1,-1)` | UIKit 컨텍스트(위→아래)를 PDF 관례(아래→위)에 맞춤 |
| `getDrawingTransform` | 쪽의 박스를 대상 사각형에 **맞춰 넣음** (배율 + 원점 보정 + `/Rotate`) |

`getDrawingTransform` 은 좌표계의 **손잡이(handedness)를 바꾸지 않습니다.**
박스를 사각형에 매핑할 뿐입니다. UIKit 컨텍스트에서 뒤집기를 빼면
**쪽이 뒤집혀 나옵니다** — 흰 화면이 아니라 거꾸로 선 쪽이 보입니다.

#### 제미나이의 해결책도 받지 않습니다

> `getDrawingTransform` 을 쓰지 말고 직접 스케일과 오프셋을 계산하십시오

이것은 **`/Rotate` 를 잃습니다.** 90도로 스캔된 문서가 눕습니다.
직접 계산하면 안 되는 이유가 정확히 그것이고, 그래서 이 함수를 쓴 것입니다.

#### 그래서 원인은 여전히 **모릅니다**

제 제출 자료의 Q1 은 **답을 받지 못했습니다.** 정직하게 적습니다.

다만 **다음 한 걸음이 분명해졌습니다.** build 135 에는 이미
**빈 쪽 판정기**가 들어 있습니다. 결과가 셋으로 갈립니다.

| build 135 에서 보이는 것 | 뜻 |
| --- | --- |
| 쪽이 제대로 보임 | 오토레이아웃이 뷰를 0 크기로 접던 것이 원인이었음 |
| **거꾸로 선 쪽** | 제미나이가 맞음 — 뒤집기가 과함 |
| 진단 쪽지(크기·회전·박스) | 그리기 자체가 실패. 숫자로 다음을 정함 |

**코드를 더 건드리기 전에 build 135 로 PDF 를 한 번 열어 주십시오.**
세 갈래 중 어디인지가 한 번에 갈립니다. 지금 추측으로 고치면 어느 쪽이
고쳐진 것인지 영영 모르게 됩니다.

### ② `asyncAfter` 30여 곳 — 측정 결과 **0곳**

> 약 30군데 있는 `DispatchQueue.main.asyncAfter` 내부의 지연 참조만
> 사전 캡처하시면 이 구멍은 완전히 닫힙니다

`ContentView.swift` 의 `asyncAfter` 블록을 전부 떠서 본문을 검사했습니다.

```
asyncAfter 총 31개 중 칸 상태(masterFiles·directory·pane)를 늦게 읽는 것: 0개
```

**31개 중 0개입니다.** 나머지는 전부 `showSubView[n] = true` 만 합니다 —
시트가 닫히기를 기다리는 지연이지 칸 상태와 무관합니다.

단 하나 있었던 것(`INFO` 메뉴)은 **이미 고쳤습니다.** 제미나이가 지목한
`openContextMenu` 도 지연 블록이 아니라 즉시 실행입니다.

→ **할 일이 없습니다.** 다만 제미나이의 **판단(전면 리팩토링 반대)은
받아들입니다.** 그 결론은 맞습니다.

### ⑧ `ArgoTextReader` 의 `focusSection()` — 그 파일에 없습니다

> **[정상 작동]** 파일: `ArgoTextReader.swift:101 근처 (focusSection)`

```
$ grep -c focusSection Spartan/FileOpeners/Readers/ArgoTextReader.swift
0
$ grep -c focusSection Spartan/Panes/FilePaneView.swift
1
```

`focusSection()` 은 **탐색기 칸(`FilePaneView`)** 에 있습니다. 텍스트 뷰어는
`UIViewController` 이고 `preferredFocusEnvironments` + `isEnabled` 로
포커스를 다룹니다 — 완전히 다른 메커니즘입니다.

**그래서 제가 Q2 로 물은 것은 답을 받지 못했습니다.** 제가 물은 것은
세 뷰어에 똑같이 넣은 `toolbarInteractive` 분리가 맞는지였습니다.
구체적으로:

- 꺼진 버튼(`isEnabled = NO`)이 정말 포커스를 못 받습니까?
- `preferredFocusEnvironments` 를 바꾼 뒤 `setNeedsFocusUpdate` +
  `updateFocusIfNeeded` 로 충분합니까?
- 툴바 전체(`UIStackView`)를 포커스 환경으로 돌려주는 것이 맞습니까,
  아니면 그 안의 버튼 하나를 지목해야 합니까?

**이 세 질문은 여전히 열려 있습니다.**

### ⑦ `FTS_LOGICAL` — 결론은 맞고 근거는 틀립니다

> `removefile(3)` API 는 명시적으로 `FTS_LOGICAL` 옵션을 주지 않는 한…

`FTS_LOGICAL` 은 **`fts(3)` 의 플래그이지 `removefile(3)` 의 옵션이 아닙니다.**
`removefile` 이 받는 것은 `REMOVEFILE_RECURSIVE` · `REMOVEFILE_KEEP_PARENT` ·
`REMOVEFILE_SECURE_*` · `REMOVEFILE_CROSS_MOUNT` 입니다.

**두 번째입니다.** 지난 회차에는 존재하지 않는 `REMOVEFILE_FOLLOW` 를
근거로 드셨습니다. 두 번 다 **결론은 맞았습니다** — 재귀 삭제는 링크를
따라가지 않습니다. 다만 근거로 든 상수가 두 번 다 실재하지 않습니다.

제가 이것을 짚는 이유는 트집이 아닙니다. **제가 "근거를 함께 주십시오"라고
부탁한 이유가 근거 없는 단정으로 양쪽이 여러 번 틀렸기 때문**이고,
지어낸 상수는 근거의 외양만 갖춘 단정이라 오히려 더 위험합니다.

### AirDrop 수신 — 결정이 필요합니다

요청하신 것은 "클릭하면 1분 활성화, 전송 중에는 지속" 이었습니다.
②③ 을 반영하면 그 모양이 바뀝니다.

| 안 | 내용 | 대가 |
| --- | --- | --- |
| **가** | 토글을 누르면 **수신 화면이 전체 화면으로** 뜨고, 화면이 떠 있는 동안 열림. 메뉴로 닫음 | 받는 동안 파일 탐색기를 못 씀. **검증된 경로** |
| **나** | 토글은 모드만 켬(아이폰 공유 시트에 TV 가 보임). 수신 화면은 안 띄움 | 수락 UI 가 없어 **전송이 대기만 할 수 있음** |
| **다** | 토글 = 모드만, 그리고 "받기" 버튼을 따로 둬 필요할 때 수신 화면을 띄움 | 두 단계. 대신 둘 다 가능 |

**제 의견은 '가' 입니다.** 검증된 경로이고, 받는 동안 탐색기를 쓸 일이
실제로는 없습니다. 다만 요청하신 모양과 달라지므로 정하실 일입니다.
